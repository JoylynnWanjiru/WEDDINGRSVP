From a paper card to a living invitation

01
The idea

The problem we solved

Printed cards can't be tracked, can't be taken back, and can't tell an usher who belongs at the gate. The system swaps each card for a private link that knows who it belongs to.

With paper cards
  • "I never got one": no proof either way
  • A photographed card brings extra people
  • Headcount for the caterer is a guess
  • Venue and timings repeated over 50 phone calls
  • At the gate, anyone confident walks in
  • Printing and delivery cost money
With personal links
  • The dashboard shows sent, opened and viewed
  • The couple can revoke a link, and it stops working everywhere
  • Each guest names the people coming, within a set limit
  • Venue, map and programme live on one page
  • Each approved guest gets a QR gate pass, checked live
  • Running cost: KSh 0

The whole system in one sentence

The couple sends each guest a personal link → the guest responds with their named party → the couple (or the system, within the allowance) approves → the guest unlocks the venue and a gate pass that ushers scan on the day.

And one guarantee above everything: nobody sees event details or gets through the gate without an approved invitation, and approval can be withdrawn at any moment.

What kind of app is this?

Main

Workflow app

One central object, the invitation, moves through stages, and what you can see depends on its stage.

Second

Content app

The couple edits the programme, venues, FAQ and story without touching code.

Small but critical

Real-time slice

Gate check-in on the day, where speed and patchy signal matter.

Naming the type early tells you where to spend effort: here, the lifecycle and the access rules matter most.

Real world

A hotel with key cards

A guest's key card opens their own room, never someone else's. Housekeeping (the usher) has a card that opens a service corridor, not the safe. The manager (the couple) has the master key. The lobby (the home page) is open to anyone, but there's nothing private in it. The capability is the key; what each person actually does with it is written in the activity log, like the hotel's door-entry records.

Check yourself
An usher scans a pass. Can they see the guest's phone number?

No. Ushers see the name and party size only. Phone numbers and emails never appear on usher screens, in QR codes, or in URLs (§13 sensitive data).

Why do the couple and the planner share one login in v1?

Decision D6 / A5: it's simpler, and a shared login can't tell them apart anyway, so a "planner can't delete" rule couldn't be enforced. Deletion is guarded by a typed confirmation phrase instead.

Check yourself
Why don't pages in app/ contain business logic?

So the logic can be tested without a browser, reused by pages, API routes and emails alike, and changed in one place. Pages "parse input, call a service, map the error" and nothing more.

Why is the database in London and not Nairobi?

Neon's free tier offers set regions, and Vercel's function region was set to the same city ("regions": ["lhr1"] in vercel.json). Keeping the app beside its database matters more than distance to the user, because one page can make several database calls.

04
The design

The stack, and why each piece

Three filters picked every tool: free to run (KSh 0 budget), one language everywhere (TypeScript), and no extra accounts where a plain link would do. Each card also shows what was rejected and why.

TypeScriptLanguage

One language for pages, server and scripts. Types catch mistakes before they run, like passing a guest where a vendor is expected.

Not separate front-end and back-end languages: twice the context-switching for one developer.

Next.js 16Framework

Pages, server actions and API routes in one project. Server components keep secrets on the server; partial prerendering serves a static shell instantly.

Not a separate React app + Express API: two deployments, two sets of bugs.

Vercel HobbyHosting

Push to GitHub → live in about a minute. Free HTTPS, daily cron jobs, London region.

Limit: personal, non-commercial use only. Selling it to other couples later means moving to Pro.

Neon PostgresDatabase

A real relational database, free for 1 GB. It sleeps when idle and wakes in about a second.

Not Supabase free: it pauses after a week idle and needs a manual restart. Bad news three weeks before a wedding.

Drizzle ORMDatabase code

Tables written in TypeScript, typed queries, and generated migration files committed to git.

Not raw SQL strings: a typo in a column name would only fail at runtime.

ZodValidation

Every form and API body is checked on the server, with friendly messages. The browser's checks are a convenience; the server's are the law.

joseSigned tokens

Signs gate passes and login sessions (JWT, HS256), so they can't be forged or edited.

Gmail + NodemailerEmail

Free, about 500 recipients a day, sent from the couple's real address.

Not Resend or Postmark: they need a paid domain, and Resend's free tier caps at 100 a day.

wa.me linksWhatsApp

One tap opens WhatsApp with the message ready; the couple presses send from their own phone.

Not the WhatsApp Cloud API: it charges per message.

qrcode + html5-qrcodeQR codes

The server draws each pass QR as SVG; ushers scan in the phone browser, no app to install.

Tailwind CSS 4Styling

Theme colours as CSS variables in globals.css, so every page uses the same burgundy and gold.

Vitest + PGliteTesting

PGlite is real Postgres running in memory: tests run the true migrations with no network and no account.

Not mocked databases: they pass while the real SQL fails.

Real world

Choosing a venue on a budget

You don't hire a stadium for 300 guests, and you don't pick the cheapest hall if it locks its doors when nobody visits for a week (that's Supabase free). You pick a place that fits the guest count, opens on demand (Neon wakes in a second), and costs nothing until you grow (Vercel Hobby → Pro). The plan already notes when to upgrade: when other couples start paying.

Check yourself
Why does lib/gate-offline.ts live outside server/?

Because the usher's phone runs it too. It checks passes offline in the browser, so it can't import anything server-only, like the database or the secret. The server reuses the same tokenFromScan(), so phone and server read QR codes identically.

What does "backend first" buy you?

Every rule had a passing test before any page used it. When the pages came, they only had to call services that already worked, so bugs were UI bugs, not rule bugs.

Rules the database itself enforces

CHECK arrived_count ≤ party_size

Even if code had a bug, Postgres refuses to let more people in than the party holds (BR-14 backstop).

UNIQUE (wedding_id, phone)

Two invitations can't share a phone number, so nobody gets invited twice by accident (BR-21).

UNIQUE client_ref

An offline check-in uploaded twice is only counted once.

One primary per party

A partial unique index: each party has exactly one main guest.

Real world

Timestamps vs statuses (D2)

Think of a parcel. Its status is where it is in the process: packed, shipped, delivered. The tracking events are facts with times: scanned at Nairobi hub 09:12. The first design had a status called PASS_ISSUED that only arrived once the pass email went out, so a guest whose email failed would have been turned away at the gate. Fix: a status says where the guest is (approved); delivery facts like pass_emailed_at are timestamps beside it.

    Check yourself
    Why does adding a person send an approved guest back to waiting, but removing one doesn't?

    BR-8: a new person is someone the couple hasn't agreed to; a smaller party is never a risk. Replacing a name counts as adding, because a different person would arrive at the gate.

    What stops a bug from setting status to "arrived" straight from "draft"?

    nextStatus() in status.ts only allows the moves in the diagram and throws INVALID_TRANSITION otherwise. Every change is also written to activity_log in the same database transaction.

    The rules

    Business rules & what-ifs

    A business rule is a promise the system keeps every time (BR-1 to BR-23). An edge case is an awkward real-life moment it must handle (E1 to E27). Each has its own test.

    BR-1 · Access

    Venue, programme, story and pass go only to approved, partially arrived or arrived guests.

    BR-4 · Access

    A wrong or made-up link looks exactly like no link, and never hints whether it ever existed.

    BR-5 · RSVP

    Party size = 1 + named extras, and extras ≤ seat allowance.

    BR-9 · RSVP

    Double-tapping Submit saves one response, not two.

    BR-11 · Capacity

    Going over venue capacity warns and asks twice; it doesn't hard-block.

    BR-13 · Gate

    Admit only if: signature valid, current pass version, not revoked, approved, and people left.

    BR-14 · Gate

    Arrived can never exceed party size, even with two ushers at the same second.

    BR-16 · Gate

    Admit "2 of 3 now"; the third uses the same pass later.

    BR-17 · Email

    At most 400 emails per Nairobi day; the rest wait for tomorrow.

    BR-20 · Data

    0712…, 712…, 254… all become +254712….

    BR-23 · Data

    All guest data is deleted 30 days after the wedding (Kenya Data Protection Act).

    D24 · Decision

    A Yes within the seat allowance is approved automatically. The couple can switch this off.

    What if…? (tap to see what the system does)

    E1A guest on slow 3G double-taps Submit
    One response is saved. The form also remembers a fingerprint of the last answer, so an identical resubmission changes nothing.
    E2A guest forwards their link to a friend
    The friend sees the original guest's name only. The party can't exceed the allowance, the couple sees every answer, and the first scan at the gate wins.
    E3An approved guest shares a screenshot of their pass
    First scan wins. The second shows "Already checked in at 12:14 by Gate 1", and the usher can compare names.
    E5Two ushers scan the same pass at the same second
    The admit locks the invitation's database row. One usher gets "admitted"; the other waits a moment, then sees "already admitted". See chapter 10.
    E16The free database is asleep on the first visit
    Neon wakes in about a second. On the wedding morning, open the admin once before the gates open to wake it.
    E17No signal at the gate
    The scanner keeps checking against the list it saved at the last sync, and uploads its check-ins when the signal returns.
    E22The couple revokes someone by mistake
    Restore returns them to their previous state with a new pass version, so old screenshots of the pass stay dead.
    E26An usher's phone is stolen on the day
    Tools → change the PIN, or "Sign out all ushers". Every scanner session ends at once, because sessions carry a version number that just moved on.
    E27The couple opens a guest's link to check it
    It isn't counted as the guest viewing it: "viewed" is the proof of receipt, so admin visits are ignored.

    The rules

    Security & privacy

    The core promise is privacy: the venue is only for approved guests. Six locks make that promise hold, each guarding a different door.

    auth/tokens.ts · D1

    Personal link

    A 43-character code made by HMAC from the guest's id and a secret. The database stores only its SHA-256 fingerprint, so a leaked database reveals no links.

    services/access.ts · BR-1–4

    The approval gate

    requireApproved() runs before any locked data is fetched. It returns a "proof" object that only it can create.

    jose JWT · D18

    Gate pass

    A signed token with the invitation id and pass version, and no personal data. Checked live at every scan.

    sessions.ts · D4, D5

    Admin & usher

    Password and PIN hashed with scrypt. Signed, HTTP-only cookies: 7 days for the admin, 18 hours for ushers.

    CRON_SECRET · D17

    Scheduled jobs

    Cron routes need Authorization: Bearer …, so strangers can't trigger email sends or data deletion.

    noindex · purge · BR-23

    Leave no trace

    Personal pages tell search engines to stay away; guest data is deleted 30 days after the wedding.

    Real world

    The wax seal (that's literally the logo)

    In old times a letter was sealed with wax pressed by the sender's ring. Anyone could read the address on the outside, but a broken or fake seal showed tampering. A gate pass is a sealed letter: the contents (invitation id, pass version) aren't secret, but the signature can only be made with TOKEN_SECRET, the ring nobody else has. Change one character of the pass and the seal no longer matches.

    The cleverest trick: making the compiler guard the gate

    The normal way

    "Remember to call requireApproved() before loading the programme." One forgetful afternoon and the venue leaks.

    What you built

    getApprovedContent(db, access: ApprovedAccess) needs a proof object that only access.ts can create. Forget the check and the code doesn't compile. Vendors got their own proof type, VendorAccess.

    Check yourself
    Why must TOKEN_SECRET never change after invitations go out?

    Every link and every pass is computed from it. A new secret makes new links that don't match the stored fingerprints, so every guest's link and pass would break at once (D1). That's also why Vercel needed exactly the same value as your .env.local.

    A revoked guest's link: why show nothing, not even their name?

    Their name alone confirms the link was real and who it belonged to. The page says only "This invitation is no longer active", which confirms nothing about anyone.

      The rules

      Vendors: a feature added mid-build (D25)

      A recommendation came in to include vendors. Instead of bolting them onto guests, they got their own list, sharing the gate machinery but never the guest numbers. This is how a design adapts without breaking rules.

      Reused, not copied

      Same scanner, same lock, same expiry and the same offline sync. The pass is a JWT with a different audience (vendor-pass), so a vendor pass can never be read as a guest pass.

      Kept apart

      Not counted in guest totals or capacity (BR-11). Their own dashboard line, their own meal count, their own CSV for the caterer.

      Least privilege

      Their page shows working info only: arrival time, programme, venue, contacts and the team pass. No story, no photos, no guest list.

      Rule change on record

      BR-1 used to say "approved guests only". The exception is written down as D25, with the date and the reason, never edited silently.

      Lessons from deployment day (21 Oct)

      What happened

      The first deploy showed "Please try again in a moment". The logs said Missing environment variable DATABASE_URL.

      Lesson

      A successful build doesn't mean the settings are there. Settings are read when a deployment runs, so add them first, then redeploy.

      What happened

      The home page worked but the admin login didn't: Missing … TOKEN_SECRET. It had been saved as TOKE_URL.

      Lesson

      Names must match exactly. Each page only needs some settings, so a typo hides until a page that uses it is opened. Read the logs, then compare names letter by letter.

      Check yourself
      Why did the home page work while the admin login failed?

      Settings are read lazily (server/config.ts): each feature reads only the ones it needs, when it needs them. The home page needs DATABASE_URL; login also needs TOKEN_SECRET to sign the session cookie.

      Where do you look first when the live site shows the error page?

      The runtime logs in Vercel. The error message names the exact cause, like a missing setting, and which page hit it.

      Reference

      Glossary

      Server actionA function the page calls on the server, like submitting the RSVP, without writing an API by hand.
      Route handlerA URL that returns data instead of a page, e.g. /api/scan/verify.
      MigrationA numbered SQL file that changes the database's shape, applied in order.
      ORMDrizzle: write database queries in TypeScript instead of SQL strings.
      HMACA fingerprint of data plus a secret. The same inputs always give the same result; it can't be faked without the secret.
      Hash (SHA-256)A one-way fingerprint. Easy to compute, impossible to reverse.
      JWTA small signed note: readable by anyone, but forging or editing it breaks the signature.
      scryptA deliberately slow password hash, so guessing passwords costs an attacker real time.
      Row lockSELECT … FOR UPDATE: "I'm editing this row, everyone else wait."
      IdempotentSafe to repeat: doing it twice has the same effect as once.
      Environment variableA setting outside the code, like DATABASE_URL, so secrets never sit in git.
      CIContinuous integration: GitHub re-checks every push automatically.
      Open GraphHidden page tags that tell WhatsApp which title, text and picture to show in a link preview.
      CronA job that runs on a schedule, like "every day at 9 am".
      PGliteReal Postgres in memory, so tests use the real database engine without a server.
      Partial prerenderA static shell served instantly, with the personal parts streamed in after.
      You built all of this. Planned on paper first, protected before it held data, tested before it had pages, and shipped with every decision written down.
